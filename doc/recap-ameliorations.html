Amélioration 1 — Result Pattern dans les Server Actions

app/actions/auth.ts Robustesse

La fonction setUserRole fait un throw brut si la session est absente. L'app peut planter sans message clair pour l'utilisateur. La solution : retourner un objet de résultat au lieu d'exploser.

❌ Aujourd'hui
session absente → throw Error → 💥 l'app plante → utilisateur perdu
✅ Amélioré
session absente → { success: false, error: "Non connecté" } → message clair affiché

Dictionnaire des mots-clés

Server Action

Concept Next.js

Une fonction qui tourne uniquement sur le serveur, jamais dans le navigateur. Elle commence par "use server". On peut l'appeler depuis un composant comme une fonction normale, mais le code s'exécute côté serveur.

Navigateur Serveur ───────────── ────────────────────── Bouton cliqué →→→→→→ setUserRole() tourne ici ←←←←←← résultat retourné

throw / try / catch

Gestion d'erreurs

Trois mots qui gèrent les erreurs ensemble.

throw → je signale qu'il y a un problème (comme lancer une alerte) try → j'essaie de faire quelque chose qui pourrait échouer catch → si ça échoue, je récupère l'erreur proprement

Result Pattern

Architecture

Un accord entre une fonction et celui qui l'appelle : "je ne vais jamais planter, je vais toujours te retourner une réponse claire."

{ success: true } { success: false, error: "message explicatif" }

Type union

TypeScript

Dire qu'une valeur peut être soit une chose, soit une autre. Le | se lit "ou". TypeScript t'oblige à gérer les deux cas.

type Résultat = { success: true } | { success: false; error: string } // option A ou option B

ORM (Object-Relational Mapper)

Base de données

Un outil qui te permet de parler à ta base de données en JavaScript/TypeScript au lieu d'écrire du SQL brut. Dans ton projet : Drizzle ORM.

Sans ORM : "SELECT * FROM practitioners WHERE status = 'validated'" Avec Drizzle: db.select().from(practitioners).where(eq(practitioners.status, "validated"))

JOIN SQL

Base de données

Façon de lier plusieurs tables en une seule requête pour récupérer des données liées.

Table practitioners Table tags ─────────────────── ────────────────── id: "abc" id: "xyz" nom: "Dr Martin" label: "bienveillant" JOIN → { nom: "Dr Martin", tag: "bienveillant" }

Bug silencieux

Bug

Un bug où le code s'exécute sans erreur visible mais retourne un résultat faux. Le pire type de bug : rien ne t'alerte, tu découvres le problème en te demandant pourquoi une fonctionnalité ne marche pas.


Promise.all

Asynchrone

Lancer plusieurs opérations en même temps et attendre qu'elles soient toutes finies. Comme envoyer 3 livreurs en même temps au lieu de les envoyer l'un après l'autre.

Sans Promise.all : requête 1 (2s) → requête 2 (2s) → requête 3 (2s) = 6s Avec Promise.all : requête 1 + requête 2 + requête 3 en parallèle = 2s

Zod

Validation

Une librairie de validation de données. Tu décris la forme que doivent avoir tes données, et Zod vérifie que c'est bien le cas — côté client pour l'UX, côté serveur pour la sécurité.

Focus — Postman & Sécurité

Postman, c'est quoi ?

Outil dev

Un outil qui permet d'envoyer des requêtes à un serveur directement, sans passer par une interface utilisateur. Les développeurs l'utilisent pour tester leurs APIs.

Situation normale : Utilisateur → 🖥️ Interface (bouton, formulaire) → Serveur Avec Postman : Développeur/Hacker → 📮 Postman → Serveur directement (bypasse totalement l'interface)

Pourquoi c'est un risque de sécurité ?

Sécurité

Ton interface peut cacher des boutons, désactiver des formulaires, masquer des pages. Mais tout ça, c'est du cosmétique. N'importe qui avec Postman peut ignorer ton interface et appeler tes fonctions serveur directement.

Exemple concret avec Abi : 🖥️ Interface dit : "Le bouton setUserRole est caché si tu n'es pas connecté" 📮 Postman dit : "Je m'en fiche de ton bouton, j'appelle setUserRole directement" Sans vérification serveur → n'importe qui peut changer le rôle de n'importe quel user 🚨

Ce que ton code fait déjà bien

Bon réflexe

Cette ligne dans setUserRole protège contre ça :

if (!session?.user?.id) throw new Error("Not authenticated")

Même si quelqu'un bypasse l'interface avec Postman, le serveur vérifie que la personne est bien connectée. La logique de sécurité est déjà en place — c'est un bon réflexe. L'amélioration, c'est juste de le faire avec un message d'erreur clair plutôt qu'une explosion.


La règle d'or de la sécurité web
« Never trust the client »
Tout ce qui vient du navigateur peut être fabriqué, modifié, ou envoyé par Postman.
La sécurité doit être vérifiée côté serveur.

Défense en profondeur

Architecture sécurité

Ton app a plusieurs couches de protection qui se renforcent mutuellement. Si quelqu'un casse une couche, les autres tiennent.

🚧 Couche 1 — Middleware Next.js : bloque les pages protégées
🖥️ Couche 2 — Interface utilisateur : cache les boutons et formulaires
🔒 Couche 3 — Server Action : vérifie la session même si les 2 autres sont bypassées ← setUserRole
